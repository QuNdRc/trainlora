# ТЗ: Адаптация ai_orchestrator под двухраздельный формат ответа модели

Целевой репозиторий: `C:/Users/Даниил/RiderProjects/Solution2/ai_orchestrator`

## 1. Цель

Адаптировать существующую программу (llama.cpp + FastAPI) под **двухраздельный формат ответа модели**, чтобы:

1. Человеческий текст («условный проектировщик») получал понятное пояснение, а не чистый JSON.
2. Программа по-прежнему машинно извлекала команды для планировщика.

Формат ответа модели — **точно два раздела**, как в датасетах:

```
Решение: <человекочитаемый текст на русском>

{"commands":[...],"explanation":"..."}
```

## 2. Текущее состояние (что есть)

- [`main.py`](…/main.py) — FastAPI, эндпоинт `POST /plan`.
  - `parse_state_string()` → `ParsedWorldState`.
  - Если конфликтов нет — возвращает `PlanResponse(commands=[], explanation="No conflicts detected")` и **LLM не вызывается**.
  - Иначе — RAG получает контекст СП, `build_user_prompt()` строит промпт, вызывается локальный llama.cpp backend.
  - [`_extract_json()`](…/main.py:105) — парсит **весь** ответ через `json.loads`, при неудаче срезает markdown-ограждения ```json```.
  - [`_parse_llm_response()`](…/main.py:125) — ждёт либо список команд, либо объект `{"commands":[...],"explanation":"..."}`.
  - `validate_commands()` — валидирует команды, отбрасывает невалидные.
- [`models.py`](…/models.py) — `PlanRequest`, `Command`, `PlanResponse(commands, explanation)`.
- [`prompt_builder.py`](…/prompt_builder.py) — `SYSTEM_PROMPT` + `build_user_prompt()`.
- [`llm_backend.py`](…/llm_backend.py) — клиент llama.cpp `POST /completion`, поле `lora` (имя адаптера).

## 3. Проблемы текущего кода под новый формат

1. `_extract_json()` парсит **весь** ответ как JSON. В формате «Решение: … \n {JSON}» весь ответ не является JSON → `_extract_json()` упадёт.
2. `PlanResponse` не имеет поля под свободный человеческий текст пояснения.
3. `SYSTEM_PROMPT` требует «JSON only, no commentary» — противоречит новому формату.
4. `prompt_builder` не подсказывает модели раздельный формат.

## 4. Требуемые изменения

### 4.1. Разбор двухраздельного ответа

Заменить логику `_extract_json` / добавить функцию извлечения.

Вход модели (пример):
```
Решение: Обнаружено пересечение кухни и гостиной. Сдвигаю кухню вправо за пределы перекрытия, чтобы устранить конфликт.

{"commands":[{"action":"move_target","room_id":"r1","new_tx":5.5,"new_ty":4.0,"reason":"устранить пересечение"}],"explanation":"Кухня пересекает гостиную; сдвигаю её вправо."}
```

Алгоритм `parse_two_part_response(raw: str) -> (commentary: str, commands_payload: object)`:

1. Очистить `raw` (убрать лишние пробелы/переводы по краям).
2. **Выделить JSON-блок** — это может быть:
   - последний фрагмент после последнего маркера ```json … ``` (если модель обернула в ограждение);
   - или подстрока, начинающаяся с `{` и заканчивающаяся на последней `}`.
   Для надёжности: искать первый символ `{` после раздела «Решение:» и парсить до сбалансированной закрывающей скобки (или пробовать от каждого кандидата `{` через `json.loads`).
3. **Всё, что до JSON-блока** — это `commentary` (человеческий текст). Убрать возможный префикс `Решение:`/`Решение` в начале и лишние переводы строк.
4. Распарсить JSON → объект; из него взять `commands` (список) и `explanation`.
5. Если JSON-блок не найден или не парсится — поведение как раньше: логировать `malformed_json` и вернуть 502 (или, по желанию, отдать `commentary` как `explanation` и пустые команды — на усмотрение, но зафиксировать решение).

Рекомендация для валидности: JSON-блок — это либо `{"commands":[...],"explanation":"..."}`, либо просто список `[...]` (легаси-совместимость с `_parse_llm_response`).

### 4.2. Модель ответа (models.py)

`PlanResponse` дополнить полем свободного текста:

```python
class PlanResponse(BaseModel):
    commands: list[Command] = Field(default_factory=list)
    explanation: str = Field(default="")
    commentary: str = Field(default="")   # НОВОЕ: человекочитаемое пояснение из раздела «Решение:»
    # (опционально) plan_summary / narrative — назвать единообразно
```

`explanation` остаётся машинным кратким пояснением (берётся из JSON-блока `explanation`), а `commentary` — развёрнутым человеческим текстом из первого раздела.

### 4.3. Обработка в /plan (main.py)

1. После `raw_output = await backend.generate(...)` вызвать `parse_two_part_response(raw_output)`.
2. `raw_commands` → `validate_commands(...)`.
3. Ответ:
   - `commands` = валидированные команды;
   - `explanation` = из JSON-блока;
   - `commentary` = человеческий текст из раздела «Решение:».
4. Ветку «нет конфликтов» (LLM не вызывается) оставить, но `commentary` заполнить человеческой строкой (например «Конфликтов не обнаружено, корректировка не требуется») вместо/в дополнение к `explanation`.

### 4.4. SYSTEM_PROMPT (prompt_builder.py)

Переписать, чтобы модель знала двухраздельный формат. Черновик:

```
You are an apartment layout planner. Analyze the layout and propose fix commands.
Follow exactly this two-part response format:

> Решение: <краткое человекочитаемое пояснение на русском, что ты изменил и почему>
> (пустая строка)
> {"commands":[...],"explanation":"<краткое машинное пояснение>"}

Command shapes (max 3 commands):
- {"action":"move_target","room_id":"<id>","new_tx":<float>,"new_ty":<float>,"reason":"<text>"}
- {"action":"swap","id_a":"<id>","id_b":"<id>","reason":"<text>"}
- {"action":"add_door","room_a":"<id>","room_b":"<id>","door_x":<float>,"door_y":<float>,"reason":"<text>"}

The JSON block MUST be valid JSON. The commentary must be concise and human-friendly.
```

Учесть: LLM-бэкенд шлёт `f"{system_prompt}\n\n{user_prompt}"` — промпт-инженерия должна требовать именно двухраздельный ответ.

### 4.5. Валидация — без изменений

`validate_commands()` уже корректен: отбрасывает невалидные команды по одной. Двухраздельный формат не влияет на валидацию, т.к. команды извлекаются из JSON-блока.

## 5. Критерии приёмки

1. Запрос к `/plan` с конфликтами → модель отвечает «Решение: … \n {JSON}» → API возвращает `{commands, explanation, commentary}`, где `commentary` — человекопонятный текст, `commands` — валидные команды.
2. Если модель вернула только JSON без «Решение:» — система всё равно извлекает команды, `commentary` пустой (fallback).
3. Если модель вернула «Решение: …» без валидного JSON — логируется `malformed_json`, поведение как прежде (на выбор: 502 или пустые команды + commentary).
4. Невалидная команда внутри JSON отбрасывается валидатором, остальные проходят.
5. Юнит-тесты на `parse_two_part_response`:
   - «Решение: … \n {JSON}`;
   - «```json … ```»;
   - чистый JSON (без текста);
   - текст без JSON;
   - большой комментарий с `{` и `}` внутри текста (должен корректно найти именно JSON-блок).
